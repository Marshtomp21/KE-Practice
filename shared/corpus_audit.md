# 电影语料可用性审计

审计日期：2026-09-03  
只读数据源：`code/KE-Practice-film-data/data/wikipedia_300_films_final/`  
数据分支：`film-data-v1`  
数据提交：`5191f12c2c4f7aa7823c8a7ca51b36b15735eaa5`

## 结论

**可以作为四套 GraphRAG 系统的共享 L2 语料，但需要先从 MediaWiki 源码生成统一的纯文本
文档；它更准确的名称是“中文维基电影知识与评价相关语料”，而不是纯影评语料。**

这批数据非常适合事实问答、人物-影片多跳关系、合作关系和聚合问题，也具备一定的评价、
反响和争议文本，可以用于小规模全局总结。若最终研究问题强调细粒度观点、评论者立场或
情感差异，后续仍需补充带作者和来源信息的专业影评。

## 对四套方法的适用性

| 方法 | 适用性 | 适合测试的内容 | 主要限制 |
|---|---|---|---|
| KG²RAG | 高 | 影片-导演-演员-作品的多跳证据与 Chunk 扩展 | 需将 WikiText 清洗并保留来源定位 |
| HippoRAG 2 | 高 | 跨影片人物关联、合作网络、关联式检索 | 高连接人物可能导致 PPR 热点偏置 |
| LightRAG | 高 | 局部事实、高层主题、混合查询和增量插入 | 抽取质量会受 Wiki 标记噪声影响 |
| Microsoft GraphRAG | 中高 | 类型、导演、主题、评价趋势的社区与全局总结 | 361 部影片仍属中小规模；社区报告成本需控制 |

## 数据质量风险

1. 原始正文是 MediaWiki 源码，包含模板、引用、表格和链接标记，不能原样作为最终共享
   文档；四套方法应使用同一份清洗后的纯文本。
2. 关系目标中 `NAME:` 临时 ID 占 55.23%，说明大量编剧、公司、奖项或其他目标还没有
   稳定 Wikidata ID。事实可用，但实体合并评测要谨慎。
3. 发现 3 个演员名称和 3 个导演名称仍含明显 Wiki 标记，例如 `{{...}}` 或
   `-{zh-hans:...}-`，需要在派生语料中清洗，但不能回写团队数据分支。
4. “合作”关系由共同影片推导，不是直接文本事实。用于问题生成时，gold evidence 应指向
   共同影片原文，而不是把派生关系文件本身作为唯一证据。
5. Wikipedia 的评价章节通常汇总媒体评分和公众反响，缺少稳定的“评论者-观点-论据”
   结构，不适合直接宣称能够评测细粒度观点归因。

## 图结构可用性

仅使用 4,941 条显式关系构图时：

- 图中涉及 3,561 个节点；
- 形成 2 个连通分量；
- 最大连通分量包含 3,557 个节点，占 99.89%。

这说明语料具有很强的跨影片连接性，适合 KG²RAG 图扩展和 HippoRAG 2 的 PPR 检索；
同时也需要限制扩展预算，避免知名演员、导演等高度节点带来大量无关证据。

## 公平使用协议

L2 端到端比较中：

1. 四套系统接收完全相同的纯文本电影文档；
2. 每个文档保留稳定的 `doc_id`、标题、来源 URL 和 revision ID；
3. 允许系统使用各自官方切块、抽取和构图方式；
4. `relations.jsonl` 和 `collaborations.jsonl` 默认只用于题目构造和证据核验，不作为某一
   系统的额外输入；
5. 若实验允许系统直接利用结构化关系，必须单独标为“提供外部 KG”的实验轨道；
6. 所有清洗、转换、抽样和问题生成代码仅放在 `code/reproductions`。
